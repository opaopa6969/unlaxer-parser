### Scene 1 — そもそも `create` じゃダメなの？

**☕ ヤン**: ……まあ、「欲しい」って言うなら足せばいいんですけど。でも `create(int i)` って既にあるじゃないですか。インスタンスメソッドで。何が足りないんですかね。

**👤 今泉**: そもそも、`create` と `of` の違いって何ですか？「static かどうか」以外に。

**🎩 千石**: `create` はテンプレートメソッドパターンのための道具です。`new CodePointIndex(0)` を毎回書かせることは、ユーザーに余分な認知負荷をかけている。`of(int)` は召喚呪文、`create` は内部の配線。別物です。

**😰 僕**: ...でも `new CodePointIndex(0)` って、そんなに長くないですよね。毎回書けばいい、っていう話には...。

**🎩 千石**: `Integer.valueOf(0)` を廃止して `new Integer(0)` に戻しますか？

*僕は黙って手元の紙を折る。*

→ **Gap 発見**: `create(int)` と `of(int)` の役割が設計上明文化されていない。`create` は多態用途、`of` は呼び出し側の利便性という分離が文書にも API にも存在しない。 **[Medium]**

---

### Scene 2 — int をクラス化すべき、という直感

**👤 今泉**: ちょっと待ってください。「int はクラス化すべき」という話が出ていましたよね。`of(int)` を追加するとして、その `int` は何ですか？

**☕ ヤン**: コードポイントのインデックスですね。

**👤 今泉**: じゃあ、`int` が入ってきた時点でもう型情報は失われているわけですよね。「これは文字列バイトインデックスか、コードポイントインデックスか」が。

**🎩 千石**: *立ち上がる。* 正確な指摘です。`StringIndex` は別クラスとして存在している。`CodePointIndex.of(5)` の「5」が StringIndex ではなくコードポイントオフセットであるという保証は、`int` 型には一切ない。

**😰 僕**: ...でも `of(int)` の `int` を「クラス化」って、何にすれば...？ `RawCodePoint` みたいなクラスを作るんですか？それって...

**☕ ヤン**: それはやりすぎだと思いますよ。*紅茶を飲む。* でも、せめてファクトリの javadoc に「引数はコードポイントオフセット、StringIndex ではない」と明記する義務は発生しますね。

→ **Gap 発見**: `of(int)` の `int` パラメータが何の単位かをコンパイル時に保証する手段がない。型システムが守れる範囲の境界が未定義。**[High]** ※ユーザー判断: `new CodePointIndex(int)` と等価なシンプルラッパーとして確定。javadoc で補完。

---

### Scene 3 — `ZERO` 定数とキャッシュ戦略

**😰 僕**: ...そういえば `ZERO` 定数の話もありましたね。`CodePointIndex.ZERO`。

**👤 今泉**: なぜ `ZERO` が必要なんですか？`of(0)` じゃダメなんですか？

**☕ ヤン**: パフォーマンスか、可読性か。どっちかでしょうね。`Integer.ZERO` は Java にないけど、`BigDecimal.ZERO` はある。頻繁に使う特別な値だから。

**🎩 千石**: `IntegerValue` のコンストラクタはバリデーションを走らせています。毎回 0 を渡してバリデーションを通すのは、コードの意図が見えない。`ZERO` は「これがゼロであることは設計上保証済み」という宣言です。

**👤 今泉**: `ZERO` だけでいいんですか？`ONE` は？パーサーで「1文字進む」という操作は頻出ですよね。

**☕ ヤン**: *コーヒーカップを置く。* それはキリがない。`ZERO` だけにしといた方がいい。

**😰 僕**: ...でも `IntegerValue` 側に `ZERO` の仕組みを持たせれば、全サブクラスが無料で使えるのに。今は `CodePointIndex.ZERO` と `CodePointLength.ZERO` と…各クラスで個別に書くことになりますよね。それ、同じコードが何箇所にも。

*千石が眉をひそめる。*

→ **Gap 発見**: `ZERO` 定数を各サブクラスで重複定義することになる。`IntegerValue` に `ZERO` を定義できない理由（static フィールドはオーバーライド不可）が設計的に盲点になっている。**[Medium]** ※確定: Java の制約として受け入れ、各クラスに個別定義。

---

### Scene 4 — `CodePointLength` の比較 API

**🎩 千石**: Issue #16 にもう一点あります。`CodePointLength` 同士の比較が使いにくいという指摘。`IntegerValue` には `gt`, `lt`, `ge`, `le`, `eq` が既にある。

**👤 今泉**: あるんですか？じゃあなぜ「使いにくい」と言われているんですか？

**☕ ヤン**: `sourceCpLen.value()` して `int` に変換してループしている、という記述が Issue にありましたね。`compareTo` があっても使われていないということは、知られていないか、使いにくいかのどちらかです。

**👤 今泉**: ドキュメントの問題ですか？それとも API の問題？

**🎩 千石**: API は存在する。発見可能性の問題です。`IntegerValue` に `gt`, `lt` があることを、`CodePointLength` のユーザーは知らない。型の階層が深くなるほど、継承した API は視界から消える。

**😰 僕**: ...javadoc に `@see IntegerValue` だけでも書けば...？

→ **Gap 発見**: `IntegerValue` の比較メソッド群が継承先クラスのユーザーに発見されていない。API の可視性問題。**[Low]**
