# Zero-count repetition and explicit zero-match checks

Ordinary bounded repetition executes its child at most `max` times. In Java,
`Repeat(child, 0, 0)` and other `Occurs` implementations with these bounds succeed
without resolving or parsing their child or terminator. Rust `repeat(0, Some(0))`
and `repeat_java(0, Some(0))` have the same contract. This also applies to a UBNF
`element{0}` or `element{0,0}` generated by either host.

Zero execution preserves both the consumed and matched code-point cursors,
including an existing matched cursor ahead of the consumed cursor and the
parent's cursor-reset policy. The normal empty result is committed using the
requested token kind; child tokens, captures, transactional state and child
diagnostics are not produced. Inversion does not turn the zero-count operation
into a child probe. Its own parser/transaction observers still run normally.
Success memo replay preserves the same cursor boundary.

Java's existing `Zero`, `LazyZero` and `EndOfSourceParser` deliberately retain a
different historical operation: with no terminator, try the child once and
accept only when it does not match. Existing Java terminator behavior is also
retained. Their Classic token-kind propagation, inversion, cursor reset,
propagation stoppers and diagnostic behavior remain unchanged. This operation
is not interchangeable with a pure PEG negative assertion. Custom Java
`Occurs` implementations can opt into it with `isZeroMatchCheck()`; Rust
provides `Expr::ZeroMatch(child)` / `child.zero_match()`. Rust `Expr::Eof` uses
this explicit path instead of an ordinary zero-count repetition.

Runtime constructors still accept invalid bounds for compatibility, but parsing
`min > max` fails before executing the child or terminator and preserves the
entry state. Java also rejects negative runtime bounds by ordinary parse failure;
Rust bounds use `usize`. UBNF frontends retain their syntax-stage acceptance of
reversed bounds. Generation rejects these definitions, including unused rules
and invalid children nested under a zero count. Java validation reports
`E-BOUNDED-INVALID`; both Rust generation hosts report invalid repetition bounds.

Source left-recursion analysis ignores a zero-count child's leading edges,
while continuing to examine reachable following elements. Thus
`Root ::= Root{0} 'x'` is valid and parses `x`, while
`Root ::= Root{0} Root | 'x'` still has unsupported left recursion. FIRST-set
analysis treats a valid zero count as nullable without inspecting the child.
Positive maxima and existing successful nullable-child termination keep their
previous behavior.

The independent shared expectations live in `conformance/zero-repeat/`.
`ZeroRepeatBoundaryTest` and Rust `tests/zero_repeat.rs` exercise Classic modes,
inversion, both reset policies, memoization and all diagnostic modes. The legacy
oracle separately covers zero checks and EOF through propagation stoppers.
`LeftRecursionConformanceTest` compiles and runs generated Java/Rust parsers and
mappers, and compares native/Java-host Rust files byte for byte.
`ZeroRepeatGenerationTest` verifies invalid definitions at generation entry
points; its native Rust checks require `-DrustConformance=true`.
